## [Unreleased]

### Upgrade notes

- **Re-run `deploy/ansible/setup-host.yaml` on every host.** The `caplv-hostctl` helper gains an `rmdir` action and may now also manage files under `/var/lib/caplv`, where direct kernel boot keeps its kernels.
- **`bootArtifacts.hostPath` must be `/var/lib/caplv` or a directory under it**, the only persistent directory the helper writes to. Other paths have been refused on the host since 0.3.0 and are now rejected by the webhook.
- **Add a `LibvirtExternalControlPlane`** to each Cluster whose control plane is the cluster CAPLV runs on (the OpenShift setup in the getting started guide), and name it in `spec.controlPlaneRef`. It replaces any hand-made `<cluster>-kubeconfig` Secret, though one you created yourself is left alone and keeps being used.

### Added

- `LibvirtExternalControlPlane` reports the existing control plane of the cluster CAPLV runs on to Cluster API, which until now considered it never initialized. Machines' node health is now evaluated, MachineHealthChecks remediate, the Cluster reports `Available`, and Cluster API deletes a worker's Node when its Machine is deleted. It also maintains `<cluster>-kubeconfig`, with a 24-hour token for a ServiceAccount that can do only what Cluster API needs to Nodes (#61, ADR 0007). The default, `direct-boot`, `session-mode` and `ephemeral` flavors include it.
- On a libvirt network (`network.type: network`) without a DHCP range of its own, CAPLV reserves a machine's static address for its MAC, so the guest gets an address by DHCP at first boot; a network with a range already gives it one and is left alone, since every update makes libvirt rebuild the network's firewall rules. OpenShift's ~2 KB worker pointer config therefore works, fetched from the initramfs, in place of the ~500 KB rendered config, which went stale and took minutes to read over fw_cfg (#62, #63).
- With direct kernel boot, an Ignition machine with a static address gets dracut `ip=`/`nameserver=` kernel arguments, so its initramfs has that address too (#62).
- `LibvirtHost.spec.unschedulable` cordons a host: CAPLV gives it to no new machine, offers it as no failure domain, and creates or starts no VM on it, including one stopped to reclaim the host, while VMs already running keep running. A "Cordoned" column shows it.
- `hack/aws-openshift` builds a single-node OpenShift (platform none) test environment on AWS, with RHEL 9 and 10 libvirt hosts using nested virtualization, and runs the getting started guide against it.

### Fixed

- A `LibvirtHost` pinned to its ed25519 host key, as the setup playbook and docs say, failed with a host key mismatch on any stock sshd: x/crypto prefers ECDSA, so the host showed a different key. CAPLV now tries each key type until the pinned one appears.
- OpenShift workers registered without a provider ID: CAPLV's kubelet drop-in set `KUBELET_PROVIDERID_FLAG`, which nothing reads, instead of `KUBELET_PROVIDERID`. CAPI never matched their Nodes to their Machines.
- Direct kernel boot had not worked since 0.3.0. The manager OOMed holding the kernel and a 100 MB initramfs in memory (it now streams them through an on-disk cache, `--boot-artifacts-cache-dir`), and the host helper refused the default `hostPath`.
- A machine's `HostReachable` condition stayed `False` after its host became reachable (#64).
- Deleting a machine left its empty directory under `/run/caplv` (#65).
- `setup-host.yaml` failed with more than one host (the SSH key was generated in parallel), and its final SSH check used the host's own address, unreachable from the control node for cloud instances.

### Security

- The Go toolchain floor is now 1.26.10, for GO-2026-6809 (distrust compromised intermediate certificates in `crypto/x509`), which govulncheck reports as reachable through every HTTPS download the manager makes. The builder image is pinned to `golang:1.26.10`.

### Documentation

- The getting started guide covers registering CAPLV with `clusterctl`, granting upstream CAPI the `nonroot-v2` SCC on OpenShift, the external control plane, and choosing between the pointer and rendered worker configs.

## [0.3.0] - 2026-10-20

### Upgrade notes

Before upgrading from 0.2.x (each item is detailed below):

- **CAPI v1.11 or later** is required; CAPLV implements only the v1beta2 contract.
- **Re-run `deploy/ansible/setup-host.yaml` on every host.** Privileged host operations now go through the `caplv-hostctl` helper it installs, and the old sudoers rules are replaced.
- **Set `spec.hostKeyFingerprint` on every `LibvirtHost`**, or run the manager with `--allow-insecure-host-keys`; an unpinned host no longer connects.
- **`http://` and other unauthenticated base-image and boot-artifact sources are refused** unless the manager runs with `--allow-insecure-image-transport`.
- **`secretRef` and `credentialsSecretRef` must name a Secret in the referencing object's own namespace**, and `spec.nodeLabels`/`spec.nodeAnnotations` may not use the `kubernetes.io`, `k8s.io`, `node-role.kubernetes.io` or `node-restriction.kubernetes.io` domains.
- **Manager flags are double-dash** (`--flag`), and logs are JSON by default.
- **The `topology` flavor** no longer creates `LibvirtHost`s and its host variables are gone: register hosts first, labelled `caplv.infrastructure.cluster.x-k8s.io/role=control-plane` or `=worker`, each with a `spec.machineNetwork`.
- Go importers: the module path is now `github.com/on-prem-spot/cluster-api-provider-libvirt`.


### Security

- A scheduled `govulncheck` workflow now runs weekly and on pull requests touching Go sources or the module files, so vulnerability findings are no longer gated on someone happening to look. Adding it surfaced 49 reachable vulnerabilities, all cleared in this release: the bulk were in the Go standard library and are fixed by the 1.26.9 toolchain floor noted under Changed (`crypto/tls`, `crypto/x509`, `net/http`, `net/url`, `net/textproto`, `net/mail`, `html/template`, `encoding/asn1`, `encoding/xml`, `mime`, `net`, `os`), with the remainder covered by raising `golang.org/x/crypto` to v0.57.0, `golang.org/x/net` to v0.60.0, `golang.org/x/text` to v0.42.0, `google.golang.org/grpc` to v1.83.1, `go.opentelemetry.io/otel` and its OTLP exporters to v1.45.0, and `oras.land/oras-go/v2` to v2.6.2. Dependabot now tracks Go modules and GitHub Actions.
- `LibvirtHost.spec.secretRef.namespace` and the `credentialsSecretRef.namespace` fields on `LibvirtCluster.spec.baseImage` / `spec.bootArtifacts` honoured an arbitrary namespace. The manager holds cluster-wide `secrets` `get;list;watch`, and these same specs choose the endpoint the credential is then sent to, so anyone able to write a namespaced `LibvirtCluster` or `LibvirtHost` could name a Secret they have no RBAC to read and have it delivered to a server of their choosing. All four resolution sites now confine the reference to the referencing object's own namespace; an empty value still means "my own namespace", and any other value is rejected with an error naming both. The field remains in the API (stored objects stay valid) and is documented as deprecated.
- `kubelet-serving` CSRs were auto-approved with any IP SAN that was merely routable, non-loopback and non-multicast. A node holding its own kubelet client credential could therefore obtain a cluster-CA-signed *server* certificate carrying a peer's address — or a service or API address — and, given a network position on the shared bridge, impersonate that endpoint to anything trusting the cluster CA. This is why `kube-controller-manager` never auto-approves this signer. Every IP SAN is now checked against the machine's `spec.network.addresses`, which the approver already had in hand; an empty address list permits no IP SANs rather than all of them.
- The sudoers rules installed by `deploy/ansible/setup-host.yaml` could not confine a path. In a sudoers command *argument* — unlike the command path — `*` matches `/` as well, and sudo compares the literal `argv` without canonicalising it, so `NOPASSWD: /usr/bin/tee /run/caplv/*` equally permitted `tee /run/caplv/../../etc/sudoers.d/x`. The same held for the `rm`, `mount`, `umount`, `rmdir`, `mkdir`, `install` and `chmod` rules, making the advertised "restricted sudo" equivalent to unrestricted root for the service account. The account now has sudo for exactly one command, `/usr/local/sbin/caplv-hostctl`, which resolves every path with `realpath -m` (collapsing `..` and resolving symlinked components) and refuses anything outside `/run/caplv`; the tmpfs `size=` argument is matched against the tmpfs size grammar so a comma cannot smuggle in a second mount option.
- The staged ignition config — the cluster's worker bootstrap payload, containing the kubelet bootstrap credentials — was written `0644` inside a `0755` directory on hosts that by design run incumbent workloads alongside other local users. It is now `0640 root:qemu` under `0750` in system mode, and `0600`/`0700` owned by the service account in session mode. The per-machine ephemeral tmpfs is mounted with an explicit `mode=` as well: a bare `mount -t tmpfs` leaves the mount root at tmpfs's default `1777`.
- `.dockerconfigjson` credentials were selected by a substring host match and then by "whatever entry is present", and the HTTPS base-image path passed an empty host, which matched everything. Since the host derives from a user-supplied reference or URL, a credential issued for `quay.io` was handed to any registry the spec named (`quay.io.attacker.example` matched on substring; an unrelated host fell through to the first entry). Selection is now an exact host match, with URL-form keys reduced to their host and the Docker Hub aliases folded together; no matching entry means no credential rather than an arbitrary one.
- Node labelling and deletion located the Node by the name `ArtifactBaseName` builds and acted on whatever came back. That name joins namespace, cluster and machine with an unescaped `-`, so distinct `(cluster, machine)` pairs collapse onto one string — cluster `prod` with machine `worker-1` and cluster `prod-worker` with machine `1` both render `caplv-prod-worker-1` — letting one machine relabel or, on teardown, delete another machine's Node and evict its workloads. Both paths now require the Node's `providerID` to match the one CAPLV injected into this machine's ignition.
- `spec.nodeLabels` and `spec.nodeAnnotations` accepted any key and were applied with the controller's cluster-scoped identity, so an author holding only namespaced `LibvirtMachine` rights could set keys that decide scheduling and policy (`node-role.kubernetes.io/master` on a worker, topology labels) — the escalation NodeRestriction exists to prevent for kubelets. Keys in the `node-restriction.kubernetes.io`, `node-role.kubernetes.io`, `kubernetes.io` and `k8s.io` domains and their subdomains are now refused at admission, as are CAPLV's own `libvirt-managed-labels` / `-managed-annotations` keys (settable directly, they would let an author name any pre-existing label as CAPLV-managed and have the next reconcile delete it). Third-party keys such as `dynatrace`, `aqua` and `k8s.ovn.org/egress-assignable` are unaffected. On update only the keys a change introduces or alters are checked, so a machine created before this restriction keeps reconciling rather than being wedged by the controller's own `providerID` write.
- Base images could be fetched over a plain `http://` URL, and both base images and boot artifacts honoured `plainHTTP`, `s3.insecure` and `insecureSkipTLSVerify` unconditionally. These bytes become the root disk and the kernel every worker VM boots, so an unauthenticated transport lets anyone on the network path choose what those nodes run. Both resolvers now refuse such a source by default. Note this closes in-transit substitution only: `spec.baseImage` `sha256` remains optional, so a compromised origin is still not detected.
- An empty `LibvirtHost.spec.hostKeyFingerprint` fell through to `InsecureIgnoreHostKey`, which accepts any host key and therefore any impersonator; the field is optional, there is no `LibvirtHost` webhook, and nothing warned, so a host registered without it connected unverified and still reported `Ready`. That channel carries the worker ignition config to the host, so whoever answers on the host's address receives the cluster's bootstrap credentials and can feed back forged `virsh` output as authoritative capacity and domain state. An unpinned fingerprint is now an error.
- Kernel and initramfs bytes were read with an unbounded `io.ReadAll` and then decompressed with another one, and the result was cached for the process lifetime. A pinned `sha256` is no defence, because the digest can only be verified once the bytes are already in hand — so a decompression bomb is spent before verification runs, and against the `128Mi` limit the shipped manifest sets, a ~1 MB response expanding to 512 MB OOM-kills the manager into a crash loop. Reads are now capped (erroring rather than truncating, so a capped read cannot be mistaken for a complete artifact) across the response body, S3 object, OCI blob and decompressed stream, with a smaller cap for OCI manifests; the base-image path, which streams to a 20 GiB cache volume, is capped too.

### Added

- Host selection (ADR 0006, phase 1). A `LibvirtMachine` can set `spec.hostSelector` instead of `spec.hostRef` (exactly one is required): CAPLV claims the first free, ready `LibvirtHost` by name whose labels match and that has the capacity asked for, honouring the failure domain CAPI chooses (as `KubeadmControlPlane` does to spread machines). The claim is the host's new `spec.consumerRef`, made with an optimistic-lock update so two machines cannot take one host, and released only after the VM and its artifacts are deleted; pinned machines claim their host too. The machine reports its host in `status.hostRef`, rebuilt from the claim when lost (e.g. by `clusterctl move`). With no free host the machine waits with `HostAssigned=False`, reason `NoHostAvailable`. `LibvirtHost.spec.machineNetwork` gives the network of the VM a host runs, and a machine takes each field it leaves unset in `spec.network` from there, so `spec.network`, its `type`, `name` and `addresses` are now optional. Templates and the ClusterClass can therefore run more than one replica. The machine controller needs `update` and `patch` on `libvirthosts`. `LibvirtCluster.spec.controlPlaneHostSelector` limits which hosts are marked control plane failure domains, so `KubeadmControlPlane` only hands its machines hosts they can claim; the ClusterClass sets it.
- The cloud-init meta-data carries the machine's provider ID as `provider_id`, which bootstrap data reads as `{{ ds.meta_data.provider_id }}`.
- An end-to-end suite on real KVM (#23). `test/e2e-libvirt` is a separate Go module using `sigs.k8s.io/cluster-api/test`: clusterctl installs CAPI v1.14.3, the kubeadm providers and CAPLV built from the checkout into a kind management cluster, and Cluster API's quick-start spec builds a workload cluster from the `topology` flavor (one control plane VM and one worker VM), checks that the Cluster is Available and the Machines Ready, and deletes it. The new `E2E (libvirt)` workflow runs it on every pull request on a GitHub runner set up as the libvirt host, with the guests' serial consoles uploaded alongside the usual logs. Run it elsewhere with `make test-e2e-libvirt`.
- cloud-init guests get their static addresses from CAPLV: the NoCloud ISO now carries a `network-config` (version 2) built from `spec.network`, matched to the NIC by MAC address, which cloud-init applies with the guest's own network stack. Unless `spec.network.macAddress` is set, CAPLV derives a stable MAC from the domain name in QEMU's `52:54:00` range, so it is known before the domain is defined. Enterprise Linux (NetworkManager) guests therefore work as well as netplan ones, and the e2e suite now also runs with CentOS Stream 9 guests.
- `clusterctl move` support. The `LibvirtHost` CRD carries the `clusterctl.cluster.x-k8s.io/move` label and the `LibvirtClusterIdentity` CRD `clusterctl.cluster.x-k8s.io/move-hierarchy`, so hosts and identities move with the clusters that use them; previously they were left behind and the moved `LibvirtMachine`s named hosts the target did not have. The controller makes each identity an owner of its Secret so the Secret moves with it (deleting an identity now deletes its Secret), which needs `patch` on Secrets through a new Role confined to the manager's namespace. `secretRef` Secrets must be labelled `clusterctl.cluster.x-k8s.io/move` by their owner. A new test runs clusterctl's move between two envtest API servers. See ADR 0005.
- `LibvirtClusterIdentity`, a cluster-scoped SSH credential that `LibvirtHost`s reference with `spec.identityRef` instead of `spec.secretRef` (#41). Its Secret lives in the controller's namespace, so host authors use the key without being able to read it, one key serves hosts in many namespaces, and replacing the Secret (or pointing `spec.secretName` at a new one) rotates it for every host at once. `spec.allowedNamespaces` decides which namespaces may use it, by name or label selector; unset allows none and `{}` allows all. A host must set exactly one of `secretRef` and `identityRef`, so `secretRef` is no longer required. The manager reads its namespace from `POD_NAMESPACE`, now set in the shipped Deployment, or `--identity-namespace`, and needs `get;list;watch` on `libvirtclusteridentities` and `namespaces`. See ADR 0004.
- `LibvirtMachine` reports a `Ready` condition covering its whole lifecycle, which CAPI mirrors into the Machine's `InfrastructureReady` condition. While provisioning it follows `InfrastructureReady` or whichever condition is holding provisioning back; after a terminal failure it is `False` with the failure's reason; while the machine is being deleted it is `False` with reason `Deleting`. `LibvirtCluster` and `LibvirtMachine` also report a `Paused` condition when they or their Cluster are paused.
- `--watch-filter=<value>` restricts a manager to objects labelled `cluster.x-k8s.io/watch-filter=<value>`, so several CAPLV instances can share one management cluster. The filter applies to every controller and to the `Cluster`/`Machine`/`LibvirtMachine` watches feeding them. The CSR approver applies it through the backing `LibvirtMachine`'s label, since CSRs carry none, so one instance never approves kubelet CSRs for another tenant's nodes.
- Each `LibvirtHost` is now reported as a failure domain: `LibvirtCluster.status.failureDomains` lists the hosts in the cluster's namespace (control-plane eligible, hosts being deleted excluded), and `LibvirtMachine.status.failureDomain` names the machine's host. CAPI copies these onto `Cluster.status.failureDomains` and `Machine.status.failureDomain`. Placement is still chosen by `spec.hostRef`.
- `status.initialization.provisioned` on `LibvirtCluster` and `LibvirtMachine`, set alongside `status.ready`. See Fixed.
- Validating webhooks for `LibvirtCluster` and `LibvirtHost`. `LibvirtCluster`: control plane endpoint port and host/port pairing; boot artifact and base image sources must set exactly the member matching `type`, with absolute URLs, bare hex `sha256` digests, `host[:port]` S3 endpoints and non-URL OCI references; the endpoint is immutable once set; insecure transports draw a warning when `--allow-insecure-image-transport` is off. `LibvirtHost`: an SSH URI selecting `/system` or `/session`, an OpenSSH `SHA256:` fingerprint, a `secretRef` in the host's namespace and absolute firmware paths; the URI cannot change while any `LibvirtMachine` is placed on the host; a missing fingerprint warns. `LibvirtClusterTemplate` now applies the same cluster rules to its templated spec.
- A feature gate framework (`feature/`, `--feature-gates`). No gates are defined yet.
- Cluster template flavors `direct-boot`, `session-mode`, `ephemeral` and `topology` (with the `libvirt-kubeadm` ClusterClass), published with each release.
- Generated CRD API reference at `docs/api-reference/v1alpha1.md` (`make api-docs`).
- `make verify` runs license-header, shellcheck, generated-code and `go mod tidy` checks, backed by scripts in `hack/`.
- ADR 0003 plans the API promotion straight to `v1beta2`.

- A defaulting webhook on `LibvirtMachine` records `spec.rootDisk.baseImagePool` as the root disk's storage pool when it is left empty. An empty value already meant that, resolved separately by the controller and the validating webhook, but nothing wrote it down -- so `kubectl get libvirtmachine -o yaml` did not say which pool would be read. Both readers keep their fallbacks, since defaulting applies at admission and machines created earlier still carry an empty value. Nothing else is defaulted: `domain.vcpus` and `domain.memoryMB` left at zero are the documented request to size the VM from the host's spare capacity, and an empty `rootDisk.ephemeralPoolSize` omits the size from the tmpfs mount so the kernel default applies -- both would be changed, not clarified, by a default.
- `LibvirtClusterTemplate`, the type a ClusterClass references through `spec.infrastructure.ref` to stamp a `LibvirtCluster` per cluster in a topology. Its absence was what stopped ClusterClass from naming a CAPLV infrastructure template at all. A validating webhook keeps the templated spec immutable, rejects a control plane port set without a host (which would be stamped onto every cluster and fail each identically), and warns when a template carries an endpoint at all, since one address copied onto every cluster is rarely intended. The ClusterClass topology *flavor* #6 also asked for is not included: a ClusterClass must name a control plane template, and choosing one (kubeadm or otherwise) is a decision about this provider's RHCOS/ignition bootstrap path rather than a mechanical addition.
- `LibvirtMachineTemplate`, the type `MachineDeployment` and `KubeadmControlPlane` reference through `spec.infrastructureRef` to stamp out a machine per replica. Its absence was what stopped those higher-order resources from being used at all. A validating webhook applies the `LibvirtMachine` spec rules to `spec.template.spec`, so a template cannot create machines that direct creation would have refused, and the templated spec is immutable, as it is for other providers: machines already stamped are not restamped, so editing a template in place would leave running machines silently not matching it. **A replica count above one does not work yet.** A `LibvirtMachine` names its host through the required `spec.hostRef` and declares a static address, and a host runs exactly one VM, so every machine from one template asks for the same host and the same address. The webhook warns about this on create rather than rejecting it, since admission cannot see the replica count and a single-replica control plane is legitimate. Scaling needs per-machine host and address allocation, which is not implemented.
- All three controllers now emit Kubernetes Events, so `kubectl describe` on a machine shows how it reached its current state rather than just the state. `LibvirtMachine` reports the domain and storage lifecycle (`DomainDefined`, `DomainStarted`, `DomainDestroyed`, `VolumeCreated`, `VolumeDeleted`, `BaseImageUploaded`, `EphemeralPoolCreated`, `EphemeralPoolDestroyed`) and warns on provisioning failures. `LibvirtHost` and `LibvirtCluster` emit on condition transitions only -- the host is health-checked on a timer whenever machines reference it, and the cluster reconciles on every `Cluster` change, so emitting per reconcile would bury the transition that actually mattered. Events are written through the `events.k8s.io` API, which the shipped RBAC grants `create` and `patch` on.
- All three CRDs now carry `categories=cluster-api`, so `kubectl get cluster-api` lists `LibvirtCluster`, `LibvirtMachine` and `LibvirtHost` alongside the core CAPI resources.
- Short names for the three CRDs: `libvirtcl`, `libvirtm`, `libvirth`.
- `LibvirtCluster`, `LibvirtMachine` and `LibvirtHost` implement `GetV1Beta2Conditions`/`SetV1Beta2Conditions`, so CAPI's condition utilities operate on them directly. These types store `[]metav1.Condition`, so the v1beta2 accessors are the applicable contract rather than the deprecated `clusterv1.Conditions` pair.
- A `capi-manager-libvirt` ClusterRole labelled `cluster.x-k8s.io/aggregate-to-manager: "true"`. The CAPI core manager discovers provider permissions through that label; without it, core controllers cannot read or patch CAPLV resources wherever CAPI's RBAC is scoped to aggregation.
- Resources annotated `cluster.x-k8s.io/managed-by` are left untouched, so a `LibvirtCluster`, `LibvirtMachine` or `LibvirtHost` whose lifecycle something else owns is no longer reconciled. Enforced both by a predicate and by an explicit check inside `Reconcile`, so a stale predicate cache cannot mutate such an object.
- The manager logs its version, git commit and build date at startup; a running pod now reports which build it is. These are injected at link time, so a binary built outside the Makefile reports `devel`/`unknown`.
- `clusterctl-settings.json` and `tilt-provider.json`, for use as a local provider in the CAPI repo tooling and the Cluster API Tilt development environment.
- `--allow-insecure-host-keys` — connect to a `LibvirtHost` with no `spec.hostKeyFingerprint`, accepting any SSH host key. Defaults to `false`; logs a warning at startup when set.
- `--allow-insecure-image-transport` — permit `baseImage` / `bootArtifacts` sources that disable transport authentication (`http://` URLs, `oci.plainHTTP`, `s3.insecure`, any `insecureSkipTLSVerify`). Defaults to `false`; logs a warning at startup when set.

### Changed

- The `libvirt-kubeadm` ClusterClass places machines by host selector: the `controlPlaneMachine`, `workerMachine` and `network` variables are replaced by `controlPlaneHostSelector` and `workerHostSelector`, defaulting to hosts labelled `caplv.infrastructure.cluster.x-k8s.io/role=control-plane` and `=worker`, and each VM takes its network from its host's `spec.machineNetwork`. The kubelet's `--provider-id` comes from the meta-data's `provider_id`. The `topology` flavor no longer creates `LibvirtHost`s, which are registered beforehand, and takes `WORKER_MACHINE_COUNT`; its host-related variables are gone. The e2e suite now runs two workers.
- The `libvirt-kubeadm` ClusterClass no longer writes a netplan file for `enp1s0` and runs `netplan apply`; CAPLV's `network-config` sets the address instead, so guests no longer need netplan or a particular interface name.
- The README is now an overview: what CAPLV is, the provisioning flow, the custom resources, the compatibility table and links. The rest has moved, unchanged apart from headings and links, into `docs/`: `getting-started.md` (prerequisites, cluster and host setup, first worker), `session-mode.md`, `configuration.md` (ephemeral storage, node labels, direct kernel boot, cluster-wide base images and private CAs, watch filters, feature gates, failure domains), `cluster-templates.md`, `architecture.md` (design decisions, host security model, storage pools), `troubleshooting.md` (MachineHealthCheck, failure modes, known limitations) and `development.md`, indexed by `docs/README.md`. Links to README sections need updating.
- Built against CAPI v1.14.3 and its v1beta2 Go API (`sigs.k8s.io/cluster-api/api/core/v1beta2`) instead of v1.9.11 and the deprecated v1beta1 API, with controller-runtime v0.24.1 and Kubernetes libraries v0.36.3. This is step 1 of ADR 0003 and changes no CRD schema: v1alpha1 now defines its own `APIEndpoint`, `ObjectMeta` and `MachineAddress` with the schema it already had, since the v1beta2 types add validation stored objects would fail. CAPI v1.11 or later remains required.
- The CRDs now carry only the `cluster.x-k8s.io/v1beta2` contract label, matching `metadata.yaml`. **CAPI cores that only implement the v1beta1 contract (v1.10 and earlier) are no longer supported**: they would read these objects with v1beta1 field shapes, and the list-shaped `failureDomains` fails to parse as the v1beta1 map.
- CI is split from one `build.yaml` into focused workflows: `golangci-lint`, `verify`, `go-vulncheck`, `ci` (tests, then image) and `release`, with `test` and `image` as reusable workflows. Status check names change (e.g. "Test / Build and Test"), so branch protection rules naming the old checks need updating.

- **BREAKING — `LibvirtCluster` no longer TCP-dials the control plane endpoint to decide readiness.** Infrastructure is ready once `spec.controlPlaneEndpoint` has a host and a port in range. Gating infrastructure readiness on API-server reachability deadlocks provisioning: CAPI waits for infrastructure to be ready before creating the control plane that would make the endpoint answer, so a cluster being built for the first time could never become ready. The `Ready=false` reason changes from `ControlPlaneUnreachable` to `WaitingForControlPlaneEndpoint`, and the 60s dial-and-recheck loop is gone. **Endpoint reachability is no longer monitored at all** — anything that relied on `LibvirtCluster` going `Ready=false` when the worker-facing endpoint went down must now watch it separately; API-server health belongs to control plane and node health checks. The rationale is recorded in `docs/adr/0002-readiness-and-bootstrap.md`.
- `LibvirtCluster.spec.controlPlaneEndpoint` is no longer required. This widens validation, so nothing previously accepted is now rejected. It follows from the readiness change above: an unset endpoint is a cluster waiting with reason `WaitingForControlPlaneEndpoint`, not an invalid object. It is also what lets `LibvirtClusterTemplate` omit the endpoint instead of baking one address into every cluster a topology creates.
- **BREAKING for anyone importing this project as a Go module** — the module path is now `github.com/on-prem-spot/cluster-api-provider-libvirt`, matching the repository and the CAPI convention of spelling the provider name out. It was `github.com/atgreen/caplv`, while `PROJECT` separately claimed `github.com/green/caplv`, a module that never existed. Container image references (`ghcr.io/atgreen/caplv`) are unchanged: they name a registry location, not a Go package.
- **BREAKING for source builds — the minimum Go toolchain is now 1.26.9**, raised from 1.25.7 to pick up standard-library security fixes (see Security above). The builder image is pinned to that exact patch; the `golang:1.26` floating tag currently resolves to 1.26.8, below the floor, and would fail at `go mod download`.
- **Manager log output is now structured JSON rather than human-readable console text.** zap's development mode was hardcoded on; it now defaults off and is bound to the `--zap-devel` flag, which restores the previous format. Anything parsing or eyeballing controller logs is affected.
- **BREAKING if you pass single-dash flags** — flags are parsed with pflag, giving the POSIX-style double-dash flags expected of Kubernetes components. Go's `flag` package accepted `-leader-elect`; pflag reads a single dash as shorthand, so the long form now needs two (`--leader-elect`). A single-dash long flag is not an error that names itself: the manager prints its usage and exits, which looks like it ignored the argument. The shipped manifests in `config/manager` already use `--`, so a default deployment is unaffected; custom args, wrapper scripts and systemd units need checking.
- Reconciliation is event-driven rather than polled. `LibvirtCluster` watches its `Cluster`, `LibvirtMachine` watches its `Machine` and `Cluster`, and `LibvirtHost` continues to watch referencing `LibvirtMachine`s — so unpausing a cluster, or any change to the owning object, wakes the reconciler immediately instead of waiting out a requeue interval.
- A deferred status patch that fails is now joined into the error the reconciler returns. Previously it was logged and dropped, so a failed status write looked like a successful reconcile.
- The demo and local-deployment artifacts that sat in the repository root — `deploy.sh`, `demo-setup-host.sh`, `demo-create-worker.sh`, `hosts.yaml`, `sno-install/`, `DEMO.md`, `DEMO.html` — have moved to `docs/demos/`, with a README stating that the host names and addresses in them are examples to replace rather than defaults to adopt. Any bookmark or script referencing them at the old paths needs updating; `DEMO.html` is still what the GitHub Pages workflow publishes.
- Each API type now carries an explicit `+kubebuilder:storageversion` marker. No behaviour change today with a single version, but it fixes the storage version being implicit ahead of a second version existing.
- **BREAKING — re-run `deploy/ansible/setup-host.yaml` on every managed host before deploying this release.** The controller now performs privileged host operations through `/usr/local/sbin/caplv-hostctl`, which hosts still carrying the previous sudoers rules do not have; ignition staging, remote file deletion and existence checks, and ephemeral tmpfs pool creation all fail against them. No fallback to the old commands is provided, because one would reinstate the path-confinement escape described above.
- **BREAKING** — configurations that relied on the behaviour corrected above now fail rather than silently proceeding: a `secretRef`/`credentialsSecretRef` naming another namespace, a `LibvirtHost` with no `hostKeyFingerprint` (the host reports `Ready=false`, which also stalls machine *deletion*, not just provisioning), a `baseImage`/`bootArtifacts` source with an insecure transport, and a `.dockerconfigjson` with no entry for the registry being contacted (previously any entry was used, so the pull now proceeds anonymously). The last two are restorable with the flags above; the first two require a configuration change.
- A Node that has not reported a `providerID` is no longer deleted when its machine is torn down, since its ownership cannot be established. A machine whose provider-id injection failed can therefore leave an orphan Node object behind.
- Unqualified OCI references now resolve to `docker.io` rather than to their first path component, matching the usual registry-detection rule (`alpine:3` and `library/alpine:3` both resolve to Docker Hub). This affects which `.dockerconfigjson` entry is selected for such references.

### Fixed

The first five were found by the new end-to-end suite.

- cloud-init guests never bootstrapped. go-diskfs ignores `FilesystemSpec.VolumeLabel` for ISO9660, so the NoCloud seed was labelled `ISOIMAGE` rather than `cidata` and cloud-init disabled itself; and without Rock Ridge, `user-data` and `meta-data` were stored as `USER_DAT` and `META_DAT`. The label is now set when the ISO is finalized, with Rock Ridge names, and the unit tests check both. The ignition ISO builder had the same defect.
- Creating a `LibvirtMachine` through the API (which is how CAPI creates every one) failed in any install from the shipped manifests: cert-manager's CA was injected into the validating webhook configuration only, so calls to the `LibvirtMachine` defaulting webhook failed TLS verification. The mutating configuration now gets the annotation too.
- The `libvirt-kubeadm` ClusterClass was rejected by CAPI: its placement patches replaced `network/addresses/0`, and CAPI does not allow patches into array elements. They now replace the whole list.
- Nodes could not register when `<namespace>-<cluster>-<machine>`, which CAPLV used as the hostname, was longer than 63 characters, as names CAPI generates often are. The guest hostname, and so the Node name, is now that string when it fits and otherwise a 63-character prefix ending in a hash of the whole name. The domain name and provider ID are unchanged, and the ClusterClass now builds the kubelet's `--provider-id` from cloud-init's instance ID, which CAPLV sets to the domain name, instead of the hostname.
- `LibvirtCluster` and `LibvirtMachine` set a message on their `Ready` condition while it was True, which CAPI v1beta2 summarises into the Cluster's `Available` and the Machines' `Ready` conditions as if it needed attention. True `Ready` conditions now carry no message; the `LibvirtCluster` event keeps its text.
- Terminal provisioning failures were invisible to CAPI v1.11 and later. CAPLV recorded them only in `status.failureReason`, which the v1beta2 contract no longer acts on, and several paths left `InfrastructureReady` at its previous value, including `True` on a machine that had been provisioned before. Every terminal error now sets `InfrastructureReady` and `Ready` to `False` with its reason.
- The README's `MachineHealthCheck` example declared `cluster.x-k8s.io/v1beta2` but used v1beta1 fields (`unhealthyConditions`, `nodeStartupTimeout`), so applying it failed. It now uses `spec.checks`.
- CAPI v1.11 and later never saw CAPLV infrastructure as provisioned. They pick the v1beta2 contract (which CAPLV declares) and read `status.initialization.provisioned` rather than `status.ready`, and CAPLV did not set it. Both are now set.
- The `LibvirtMachine` defaulting webhook also ran on update. A machine stored without `baseImagePool` (anything created before the defaulter shipped) got it written on its next update, which the validating webhook rejected as a change to the immutable spec. Every later update failed, including the controller's own finalizer and `providerID` patches. Defaulting now applies on create only.

## [0.2.6] - 2026-08-11

### Fixed
- The two `mount` sudoers rules added in 0.2.5 for the session-mode `uid=`/`gid=` options used a single comma-joined `-o` list (`-o uid=*,gid=*` and `-o size=*,uid=*,gid=*`), which `visudo`/`sudoers` rejects — a comma in a command spec separates commands, so `gid=*` was parsed as a second command and failed validation with `expected a fully-qualified path name`. Both the `/etc/sudoers.d/caplv` template and the `CreateTmpfsPool` mount command now emit each option as its own `-o` flag (`-o uid=* -o gid=*`), which validates cleanly and keeps the executed command matching the allowlist entry.

## [0.2.5] - 2026-08-07

### Fixed
- Session-mode ephemeral pools left volume files un-deletable — `CreateTmpfsPool` mounted the per-machine tmpfs root-owned, but on session-mode hosts the per-user daemon runs as the SSH service account (not root), so a later `vol-delete` failed to unlink volume files under `/run/caplv/<machine>` with `Permission denied` (unlink needs write access on the parent directory, which a non-root, non-owning process lacks). The tmpfs is now mounted with `uid=`/`gid=` set to the service account (session mode only), making the pool directory service-account-owned atomically at mount time — no root-owned window and no separate `chown` (which isn't in the sudoers allowlist). The setup playbook's `/etc/sudoers.d/caplv` template grew the two matching `mount` rules for the `uid=,gid=` and `size=,uid=,gid=` option combinations.

## [0.2.4] - 2026-07-17

### Fixed
- The restricted sudoers allowlist deployed by the setup playbook did not permit the `install -d -m 0755` and `chmod` commands that 0.2.3 introduced for umask-independent file writes, so on playbook-configured hosts every ignition/artifact write under `/run/caplv` would have failed with a sudo password prompt. The `/etc/sudoers.d/caplv` template now allowlists `install -d -m 0755`, `chmod 0755`, and `chmod 0644` scoped to `/run/caplv/*`.
- Session-mode `virsh start` could fail with `cannot limit core file size of process ... to 18446744073709551615: Operation not permitted` — when core dumps are enabled libvirt sets the qemu process core-file-size limit to unlimited, which the unprivileged per-user daemon cannot do while the service account's hard `ulimit -c` is capped. The setup playbook now raises the hard core limit to unlimited for both daemon entry paths: an `/etc/security/limits.d` entry for PAM (SSH) sessions and a `LimitCORE=infinity` drop-in on the service account's `user@<uid>.service` (written before lingering is enabled, so a fresh setup gets it on first start; an already-lingering user manager picks it up on its next restart).
- A pre-existing `/run/caplv` directory with a too-restrictive mode (e.g. `750 root:root`, created by a CAPLV version prior to 0.2.3 under a restrictive root umask) was not repaired by the 0.2.3 fix — `install -d` only sets the mode on directories it creates — so the unprivileged qemu process still could not traverse to the ignition file and VM start kept failing with `Permission denied`. `WriteRemoteFile` now explicitly `chmod 0755`s the parent directory on every write, including the CAPLV-owned `/run/caplv` base itself for paths beneath it, so affected hosts are repaired automatically on the next reconcile with no manual chmod needed.

## [0.2.3] - 2026-07-17

### Fixed
- VM start failed with `-fw_cfg ... can't load /run/caplv/<machine>/ignition.json: Failed to open file: Permission denied` on hosts with a restrictive root umask (e.g. `0027`) — `WriteRemoteFile` wrote host files via `sudo tee` and created directories via `sudo mkdir -p`, both of which inherit the remote root umask, so the ignition file (and boot artifacts) could come out `0640`/`0750` and be unreadable by the unprivileged qemu process. File and directory modes are now set explicitly: parent directories are created with `install -d -m 0755` (which, unlike `mkdir -p -m`, applies the mode to every path component it creates) and files are `chmod 0644` after the write, which also repairs a wrong mode left behind by a previous write.

## [0.2.2] - 2026-07-15

### Fixed
- Session-mode UEFI machines failed at `virsh start` with `Failed to create file '/var/lib/libvirt/qemu/nvram/..._VARS.fd.new': Permission denied` — the domain XML pinned every machine's NVRAM file into the system daemon's root-owned nvram directory, which the unprivileged per-user daemon can never write. On session-mode hosts the explicit NVRAM path is now omitted, so libvirt allocates the file in its own per-user nvram directory (`~/.config/libvirt/qemu/nvram/`) and removes it at undefine; `status.artifacts.nvramPath` is left empty accordingly.
- `LibvirtHost.spec.nvramTemplatePath` was silently ignored — the field existed (with its `/usr/share/OVMF/OVMF_VARS.fd` default) but was never wired into the domain XML. It is now emitted as `<nvram template=...>` for UEFI machines with an explicit `firmwarePath`, so each machine's NVRAM is initialized from the configured VARS template on both system- and session-mode hosts.

## [0.2.1] - 2026-07-15

### Changed
- Documented which storage pools CAPLV creates versus which the operator must provide: a new "Storage Pools" README section enumerates every pool referenced across the CRDs, and the `rootDisk.storagePool` / `rootDisk.ephemeralPool` CRD field descriptions now state that the ephemeral pool is a CAPLV-generated per-machine pool named `<namespace>-<cluster>-<machine>-pool` (surfaced in `status.artifacts.ephemeralPoolName`) — previously they incorrectly implied CAPLV creates a tmpfs pool under the `storagePool` name.

### Fixed
- Endless retry loop when a machine's ephemeral tmpfs pool exists but is inactive — a libvirt daemon restart (common with session-mode per-user daemons) leaves the pool defined but stopped, and every subsequent volume operation failed with `pool '...' is not active`, an error classified as transient and retried forever. `reconcileRootDisk` now detects the defined-but-inactive pool and repairs it: `pool-start` if the tmpfs backing is still mounted, otherwise destroy and recreate the pool from scratch.

## [0.2.0] - 2026-07-14

### Added
- Session-mode (`qemu:///session`) support — the `LibvirtHost` URI path now selects which libvirt daemon the controller drives on the host: `/system` (default, unchanged) or `/session` for the SSH user's unprivileged per-user daemon. In session mode QEMU runs as the service account rather than under the root-owned system daemon; bridge attachment is delegated to QEMU's setuid `qemu-bridge-helper` against bridges whitelisted in `/etc/qemu/bridge.conf`. The host-setup playbook grew a `libvirt_mode=session` variable (plus `session_allowed_bridges`) that enables user lingering, `kvm` group membership, the bridge-helper setuid bit and ACL, and creates the storage pool in the user session. Session mode only supports `network.type: bridge`; libvirt-managed NAT networks still require `/system`. A URI with any other path (e.g. a typo like `/sessions`) is now rejected at reconcile with an explicit error instead of silently driving the system daemon.
- Session-mode preflight checks. On `LibvirtMachine`: a machine that uses `network.type: network` on a session-mode host is failed terminally with a new `NetworkTypeUnsupported` reason (the per-user daemon has no network driver), instead of `virsh start` retrying forever on an opaque "Network not found". On `LibvirtHost`: session-mode hosts are additionally probed for the setup that no virsh query covers — a setuid (or `cap_net_admin`) `qemu-bridge-helper` and `loginctl` lingering for the service account — and marked `Ready=false` with a new `SessionModeMisconfigured` reason naming the missing piece; without these, VM starts fail with an opaque bridge-helper error, or worse, VMs silently die when the controller's last SSH session closes.

## [0.1.2] - 2026-06-25

### Added
- Storage-pool preflight on `LibvirtMachine` — before any volume work, the controller verifies that every libvirt storage pool the machine references exists on the target host: the cluster base-image staging pool (`LibvirtCluster.spec.baseImage.pool`), the root-disk base-image source pool (`rootDisk.baseImagePool`), the root-disk target pool (`rootDisk.storagePool`), and every `additionalDisks[].storagePool`. A missing pool is now surfaced as a terminal `BaseImagePoolNotFound` / `StoragePoolNotFound` failure with an actionable message and an `InfrastructureReady=False` condition, instead of an opaque `Storage pool not found` error from `vol-create-as` that the reconciler retried indefinitely. Pools that CAPLV provisions itself (the per-machine ephemeral tmpfs pool when `rootDisk.ephemeralPool` is set) are intentionally skipped, and pools referenced more than once are de-duplicated to a single check.
- Hypervisor capability check in the `LibvirtHost` health probe — after confirming libvirt connectivity, the controller runs `virsh domcapabilities --virttype kvm` to confirm the host can actually run the `<domain type='kvm'>` machines CAPLV defines. This catches a *partial* libvirt install (libvirt-client and the daemon present, but the QEMU/KVM driver/emulator missing or KVM unavailable) that `virsh version`/`nodeinfo` answer happily but which would fail at first machine provision. On failure the host is marked `Ready=false` with a new `HypervisorUnavailable` reason naming the likely-missing packages (`qemu-kvm` / `libvirt-daemon-driver-qemu`).

### Fixed
- Nil-pointer panic in `LibvirtMachine` reconciliation — when domain provisioning hit a terminal libvirt error (e.g. permission denied), `reconcileDomain` recorded the failure on the machine status and returned `(nil, nil)`, but `reconcileNormal` then dereferenced the nil `domainInfo`, panicking the controller. The terminal-error path now returns cleanly, persisting the recorded `FailureReason`/`FailureMessage`.
- Added `watch` permission on `nodes` to the controller `ClusterRole`. The controller establishes a cache-backed informer on Nodes whose reflector requires `watch`; the role granted only `get;list;patch;update;delete`, causing the controller-runtime cache to fail with `nodes is forbidden: cannot watch resource "nodes"`.

## [0.1.1] - 2026-06-19

### Added
- `LibvirtCluster.spec.baseImage` — cluster-wide URL-driven distribution of the root-disk qcow2. The controller fetches the qcow2 once into a content-addressed local cache (default `/var/cache/caplv/baseimages`) and streams it onto each libvirt host the first time a machine targeting that host is scheduled; subsequent machines on the same host reuse the staged volume. Supports the same three transports as `bootArtifacts` — **HTTPS**, **OCI** (single-blob artifact), and **S3** — with the same `credentialsSecretRef` shapes. Transparent gzip decompression (`*.qcow2.gz` mirrors land decompressed in the libvirt pool, and the `sha256` field describes the decompressed payload). Concurrent fetches across machines coalesce via `singleflight`; concurrent uploads to the same host are per-`(host, sha256)` mutex'd. New `BaseImageStaged` status condition on `LibvirtMachine` surfaces the first-machine-on-fresh-host wait so it doesn't look like the Machine is stuck. Removes the need to pre-stage the qcow2 in each host's libvirt pool via Ansible.
- `LibvirtCluster.spec.bootArtifacts` — opt-in switch from QEMU `fw_cfg` ignition delivery to libvirt direct-kernel-boot plus a virtio-blk ignition disk. Sidesteps the kernel `qemu_fw_cfg` O(n²) read regression (tens of seconds of wall-clock time on multi-MB ignition payloads) and shaves first-boot time accordingly. Kernel/initramfs can be pulled from **HTTPS**, **OCI** (single `oras`-style artifact, layers identified by `org.opencontainers.image.title`), or **S3** (any S3-compatible store: AWS, MinIO, Ceph RGW). Optional `kernelSHA256` / `initramfsSHA256` fields enforce integrity, and OCI/S3 sources accept a `credentialsSecretRef` for private endpoints (`kubernetes.io/dockerconfigjson` or basic-auth secrets for OCI; static-credential secrets for S3). Resolved bytes are cached in-process and content-addressed on each libvirt host so machines in the same cluster reuse the same staged files.
- `LibvirtMachine.spec.rootDisk.ephemeralPoolSize` — optional cap on the per-machine tmpfs storage pool (accepts tmpfs `size=` syntax, e.g. `"80%"`, `"8G"`). Defaults to the kernel's tmpfs default (50% of RAM).
- `LibvirtMachine.spec.nodeLabels` and `LibvirtMachine.spec.nodeAnnotations` — controller-applied Node labels and annotations that bypass the NodeRestriction admission allow-list, so arbitrary keys (e.g. `dynatrace`, `k8s.ovn.org/egress-assignable`) can be set on workers. Owned keys are tracked on the Node via `infrastructure.cluster.x-k8s.io/libvirt-managed-labels` / `-managed-annotations` annotations; admin-set labels are left untouched. Surfaced as the `NodeLabelled` status condition.
- Unified CI/CD pipeline with build, test, lint, Docker build+push, Cosign signing, SBOM generation, Trivy scanning, SLSA provenance, and release asset upload
- Container image signing via Cosign (keyless, Sigstore)
- CycloneDX SBOM generation for container images
- Trivy container security scanning with GitHub Security integration
- Go dependency vulnerability checking via govulncheck
- SLSA Level 3 provenance generation for release artifacts
- GitHub Artifact Attestation for container images
- Release artifacts follow the [CAPI clusterctl provider contract](https://cluster-api.sigs.k8s.io/clusterctl/provider-contract.html): `infrastructure-components.yaml`, `metadata.yaml`, and `cluster-template.yaml` are published as individual top-level release assets (replacing the `deploy-manifests.tar.gz` bundle), so the provider can be consumed directly by `clusterctl init`, `clusterctl generate cluster`, ArgoCD, and other tooling that expects per-file URLs
- Multi-architecture container builds (linux/amd64, linux/arm64)
- Event-driven versioning (semver for releases, date-based for main, pr-NUMBER for PRs)
- `LibvirtCluster.spec.baseImage.source.https.insecureSkipTLSVerify` — opt-in TLS verification bypass for the HTTPS base-image fetch, matching the existing knob on the `OCI` and `S3` transports. Intended only for dev/self-signed endpoints; for production mirrors fronted by a private CA, prefer adding the serving CA to the controller's trust store via `SSL_CERT_FILE` (documented under "HTTPS trust" in the README), which keeps verification on.

### Changed
- `bootArtifacts` resolvers (HTTPS, OCI, S3) now transparently decompress gzip-wrapped payloads, detected by the `1f 8b` magic bytes (no naming convention or media-type required). The `kernelSHA256` / `initramfsSHA256` integrity checks and the on-host content-addressed cache path both describe the *decompressed* payload, so a `.gz` mirror in Artifactory and a raw `vmlinuz` produce identical digests and reuse the same staged file.
- Consolidated separate CI workflows (test, lint, e2e, image) into a single unified build pipeline
- Container images now pushed to GHCR with consistent tagging across all event types
- Release workflow triggers on `v*` tag push and creates a DRAFT release for the maintainer to review before publishing (matches the CAPI ecosystem convention used by cluster-api-provider-vsphere); the previous flow ran on release-published, which left the release public if any earlier job failed
- `make build-installer` stages `config/` in a build dir before running `kustomize edit set image`, so the checked-in `config/manager/kustomization.yaml` is no longer mutated as a side effect of producing a release manifest locally

### Fixed
- `BootstrapDataReady` condition on `LibvirtMachine` is now set to `True` once the bootstrap data secret is available. Previously the condition was only ever set to `False` — its success path never flipped it — so the `False`/`BootstrapDataNotReady` state set on the first reconcile (before the bootstrap provider had created the secret) lingered indefinitely, misleading operators into thinking a fully-provisioning machine was still blocked on bootstrap.
- E2E CI failure: set CONTAINER_TOOL=docker for GitHub Actions runners
- All golangci-lint issues (gofmt, modernize, unparam, unused)
